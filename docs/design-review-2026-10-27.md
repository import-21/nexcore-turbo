# nexcore-turbo 設計見直し：1サイトの障害を他に波及させない（2026-10-27）

前提: **どんな状況でも止まらない**。1サイトの不具合・暴走・攻撃が、他のサイトに波及しないこと。
対象: Python multisite（docker/python-multisite）、PHP multisite（docker/multisite）、nginx 層。
サーバー1台が丸ごと落ちる場合（冗長化）は対象外。ここでは1台の中の話。

以下の数値（コンテナの上限、同時稼働数、cgroup の値など）はすべて説明のための例です。

---

## 1. 見直し前の作りで全サイトが止まる経路

| # | きっかけ（1サイトで起きる） | 連鎖 | 結果 | 根拠 |
|---|---|---|---|---|
| A | サイトがプロセスを増やし続ける（fork爆弾・暴走） | コンテナのプロセス枠が埋まる → 管理役の `os.fork()` が EAGAIN で失敗 → 例外を捕まえていない → **PID 1 が終了** | **全サイト停止**（コンテナ再起動まで） | multisite.py `spawn()` に try なし、`run()` にも無し |
| B | サイトがメモリを食いつぶす | コンテナのメモリ上限を超える → OOM killer がコンテナ内から1つ選ぶ。管理役（framework を preload して大きい）も候補 | 管理役が選ばれると**全サイト停止** | `oom_score_adj` 未設定 |
| C | SIGHUP 時の再スキャンで socket 作成失敗（ディスク満杯など） | `scan()` の例外が `run()` を抜ける → PID 1 終了 | **全サイト停止** | `add()` に try なし |
| D | サイトが /tmp やログに書き続ける | `TMPDIR=/tmp` は全サイト共有、ログの切り替えは起動時だけ → コンテナ/ホストのディスク満杯 | 全サイトの書き込み失敗、ホスト全体にも影響 | `become()` / `serve_site()` |
| E | アクセスが多くキャッシュが溜まる | nginx のキャッシュ（tmpfs）＋索引がコンテナのメモリ上限を超える | **nginx 停止 = 全サイト停止** | compose.yml / turbo-http.conf |
| F | turbo 本体の更新・設定変更・再ビルド | コンテナは1つ | **全サイトが同時に停止** → 全サイト同時に起動し直し | compose.yml |
| G | 同時稼働の上限を超える数のサイトが同時に処理中 | `MAX_ACTIVE` 到達。処理中のサイトは追い出されない | 上限を超えたサイトは待たされ続けて 504 | `_evict()` |
| H | CPU を使い続けるサイト | コンテナの CPU を全サイトで取り合う | 全サイトが遅くなる（止まりはしない） | CPU 上限はコンテナ単位のみ |

PHP multisite も同じ形（php-fpm のマスター1つ、DB 1つ）に加えて、全サイトが同じユーザー（www-data）で動いており、`open_basedir` だけで分けている。1サイトが乗っ取られると他のサイトのファイルも読める。

すでに良い点:
- アプリが落ちること自体はそのサイトだけで済む（1サイトを強制終了 → そのサイトだけ503、数秒で自動復帰、他は200のまま）
- 起動に失敗し続けるサイトは待ち時間を延ばしながら 503 を返し、fork を繰り返さない
- `proxy_cache_use_stale error timeout http_5xx`: アプリが落ちてもキャッシュ済みのページは出せる

### 1-2. 1サイトが乗っ取られた場合（検証用サイトのユーザーから試行）
| 試したこと | 結果 |
|---|---|
| 他サイトのファイル一覧/読み取り/書き込み、turbo.env | 防げた（サイトごとのユーザー + ACL） |
| 他サイトのソケット接続、他サイト/管理役へのシグナル、root 化 | 防げた |
| 他サイトのプロセス一覧（サイト名・コマンド）が見える | **できてしまう**（/proc が共有、hidepid なし） |
| 共有 /tmp への書き込み | **できてしまう**。umask 022 のため他サイトの一時ファイル（Django の大きいアップロード等）が読める可能性 |
| 同じ Docker ネットワーク上の DB・外部インターネットへの接続 | できてしまう（1サイト1コンテナ構成でも、同じネットワークに置けば同条件） |

→ 対策: サイトごとの TMPDIR（0700）と umask 077、/proc を hidepid=2 で見せない（または PID 名前空間をサイトごとに分ける）、
外向き通信はサイトごとに許可制（nftables の uid 一致 `meta skuid`）、DB はユーザー単位で権限と接続数を絞る。
資源の食いつぶし（1章 A/B/D/H）は乗っ取られたサイトからの攻撃としても使えるので、P0/P1 はセキュリティ対策でもある。

## 2. 設計の原則（見直し後）

1. **管理役は絶対に死なない**: 管理役のループで例外を外に出さない。失敗はそのサイトだけの 503 に変える。OOM で真っ先に殺されないようにする。
2. **1サイトの上限は、そのサイトの中で止める**: メモリ・プロセス数・CPU・ディスクの上限をサイト単位でかける。共有の上限（コンテナ全体）に届く前に、サイト自身が止まる。
3. **壊れる範囲を区切る**: 全サイトを1つのコンテナに入れない。グループ（セル）に分け、1つのセルが落ちても他は動く。
4. **落ちても見せ続ける**: アプリやセルが落ちている間も、キャッシュ済みのページを返し続ける。
5. **止めずに更新する**: 更新はセルを1つずつ。新しいものが動いてから古いものを止める。

## 3. 具体策

### P0: 小さな変更で連鎖を断つ
| 対策 | 防ぐもの | 内容 |
|---|---|---|
| 管理役の例外を捕まえる | A, C | `spawn()` の fork 失敗 → そのサイトを 503 + 待ち時間。`add()`/`scan()` の失敗 → そのサイトだけ飛ばしてログ。`run()` のループ1周ごとに例外を捕まえ、ログを出して続ける |
| サイトごとのプロセス数上限 | A | 子プロセスで `setrlimit(RLIMIT_NPROC)`。サイトごとにユーザーが違うので、上限がそのサイトだけにかかる |
| OOM で殺される順番 | B | 管理役の `oom_score_adj` を低く、サイトの子を高くする。メモリが溢れたら、管理役ではなく大きいサイトが止まる |
| nginx のメモリ | E | nginx のメモリ上限を、キャッシュの最大量＋索引より十分大きくする（またはキャッシュの最大量を下げる） |
| 落ちても見せる | 全般 | `proxy_cache_use_stale` に `http_504` と `invalid_header` を足す。`inactive` を長くして、落ちている間も古いページを返せる時間を延ばす |

### P1: サイト単位の上限（cgroup）
- サイトの子ごとに cgroup v2 の小さなグループを作る: `memory.max`、`pids.max`、`cpu.weight`（取り合いは平等）、必要なら `cpu.max`
- コンテナの中で cgroup を作るには `cgroupns: private` と cgroup の書き込み許可が必要。無理なら管理役をホストの systemd で動かし、`systemd-run --scope -p MemoryMax=...` でサイトを起動する
- ディスク: サイトごとに `TMPDIR=<サイト>/tmp`。ログは管理役がサイズを見て切り替える（起動時だけでなく）。tmp とログには上限をかける（project quota、または容量を決めたループデバイス）

### P2: セル分割と無停止更新
- 1セル = 1コンテナ = 数十サイト程度
- 割り当て表（サイト → セル）を前段の nginx の map に持つ。重いサイトは専用セル、または1サイト1コンテナ
- 更新はセルごと: 新しいコンテナを起動 → ソケットが揃ったら nginx の振り分けを切り替え → 古い方は処理中のリクエストが終わるまで待ってから停止
- `MAX_ACTIVE` はセルごとの上限になり、G の待ち行列もセルの中だけで済む

### P3: 見張りと自動復旧
- 管理役に `/healthz`（ループが回っているか、処理中サイト数、失敗中サイト）を付ける。Docker の healthcheck と外部監視の両方から見る
- セルが不健康なら自動で再起動。再起動中はキャッシュ済みページで凌ぐ（P0 の stale）
- サイトごとの 5xx 率・再起動回数・使用メモリを記録し、上限に当たり続けるサイトを知らせる

### PHP multisite
- サイトごとに別ユーザーで pool を動かす。`open_basedir` 頼みをやめる
- `pm.max_children` に加えて、pool ごとに `rlimit_core` / `process.max`、php の `memory_limit` を必ず設定
- php-fpm マスターも Python と同じくセルに分ける。DB はセルごと、または接続数の上限をユーザーごとに設定（`MAX_USER_CONNECTIONS`）

---

## 4. 進め方
1. P0 を入れる → `tests/python/matrix.sh` を通す
2. A〜E を再現するテストを追加（fork 爆弾、メモリ食い、ディスク書き込み、キャッシュ満杯）。「他のサイトが 200 のまま」を合格条件にする
3. P1 → P2 の順。P2 からは更新も無停止になる
4. 収容数のベンチを取り直す（上限をかけた分、少し落ちる可能性がある）

## 5. 実施結果

F（更新時の全停止）は今回は対象外。それ以外を実装した。値は例。

| # | 対策 | 状態 |
|---|---|---|
| A | 管理役: fork 失敗はそのサイトだけ 503 + 待ち時間。ループの例外はログを出して継続。停止シグナルは例外で失われない | 済（単体テスト） |
| A | サイトごとのプロセス上限: cgroup `pids.max` + `RLIMIT_NPROC` | 済（fork 爆弾はそのサイトの上限で停止、他サイト 200） |
| B | サイトごとのメモリ上限: cgroup `memory.max`・swap 0・`memory.oom.group`。管理役の `oom_score_adj` を低く、サイトを高く | 済（上限を超えて確保 → そのサイトだけ強制終了、他 200、自動復帰） |
| C | サイトの登録失敗（ディスク満杯など）はそのサイトだけ飛ばして、しばらく後に再試行 | 済（単体テスト） |
| D | サイトごとの TMPDIR（0700、起動時に掃除）、/tmp・/dev/shm を 1733、ログは 1 秒ごとにサイズを見て切り替え | 済。ただしサイト本体のファイル書き込みはディスク quota が無い |
| E | nginx のメモリ上限をキャッシュより十分大きくする | 済 |
| G | 同時稼働の上限 | 未対応（セル分割で対応予定） |
| H | サイトごとの CPU 上限: cgroup `cpu.max` | 済（1サイトが多数のプロセスで CPU を使い切っても、他サイトの応答の悪化は小さい） |
| — | 落ちても見せる: `proxy_cache_use_stale` に invalid_header / http_504、保持時間を延長 | 済 |
| — | 1 サイトへの接続集中: サイトごとの同時接続数の上限（`limit_conn`） | 済 |

cgroup の委任方法: ホストに `turbo.slice` を作り、`cgroup_parent: turbo.slice` + `cgroup: private` +
`/sys/fs/cgroup/turbo.slice` をコンテナの `/turbo-cg` にマウント。管理役が自分の cgroup の下に
`supervisor/` と `site-<名前>/` を作る。`docker exec` は runc が `supervisor/` に入れるので従来どおり使える。

残り: 他サイトのプロセス一覧が見える（/proc の hidepid は CAP_SYS_ADMIN が必要）、DB・外部への通信の制限、
ディスク quota（ext4 の再マウントが必要）、PHP multisite の同種対策、G。
